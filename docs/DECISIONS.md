## ADR-001: 使用 SteamVR Overlay 作为 UI 层

### 状态

✅ 已接受

### 背景

用户需要在 VRChat 中输入中文，需要一个用户界面来显示虚拟键盘和候选词。需要决定 UI 的呈现方式。

### 考虑的方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. SteamVR Overlay** | 使用 SteamVR 的 Overlay API 叠加 UI | 全局可用；不依赖 VRChat 世界；官方支持 | 需要独立的 Unity 程序 |
| **B. VRChat Udon 键盘** | 在 VRChat 世界中创建 Udon 驱动的键盘 | 原生集成 | 只能在支持的世界使用；需要世界开发者配合 |
| **C. 独立 VR 应用** | 创建独立的 VR 应用 | 完全控制 | 无法叠加在 VRChat 上；用户需要切换应用 |
| **D. 桌面窗口** | 在桌面显示窗口，通过串流看到 | 实现简单 | 用户体验差；需要看显示器 |

### 决策

选择 **方案 A：SteamVR Overlay**

### 理由

1. **全局可用**：Overlay 可以在任何 VRChat 世界中使用，不需要世界开发者做任何配合
2. **用户体验好**：UI 直接叠加在 VR 视野中，用户无需离开 VR 或切换应用
3. **官方支持**：SteamVR Unity Plugin 是官方提供的，文档和社区支持完善
4. **可扩展性**：未来可以扩展支持其他 VR 应用，不仅仅是 VRChat

### 后果

- 需要开发一个 Unity 应用（单 exe，见 ADR-009）
- 需要处理 Overlay 与 VRChat 的层级关系

## ADR-002: 使用 WebSocket 进行 VR-PC 通信

### 状态

❌ 已废弃（采用 ADR-009 单 exe 架构，不再需要进程间通信）

### 背景

VR 端（Overlay）和 PC 端（输入法服务）需要通信，需要选择合适的通信协议。

### 考虑的方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. WebSocket** | 使用 WebSocket 协议 | 全双工；库支持完善；易于调试 | 需要额外的服务器 |
| **B. TCP Socket** | 使用原始 TCP Socket | 性能高；控制精确 | 需要自己处理消息边界；复杂 |
| **C. UDP** | 使用 UDP 协议 | 延迟低 | 不可靠；需要自己处理丢包 |
| **D. 共享内存** | 使用共享内存通信 | 性能最高 | 实现复杂；跨语言支持差 |
| **E. HTTP 轮询** | 使用 HTTP 请求轮询 | 实现简单 | 延迟高；效率低 |

### 决策

选择 **方案 A：WebSocket**

### 理由

1. **全双工通信**：PC 端可以主动推送候选词到 VR 端，无需 VR 端轮询
2. **库支持完善**：Unity 和 .NET 都有成熟的 WebSocket 库
3. **易于调试**：可以使用浏览器开发者工具或专门的 WebSocket 调试工具
4. **实时性足够**：输入法的延迟要求（100-200ms）WebSocket 完全可以满足
5. **JSON 友好**：WebSocket 天然支持文本消息，与 JSON 配合良好

### 后果

- PC 端需要运行一个 WebSocket 服务器
- VR 端需要处理连接断开和重连
- （已废弃：当前为单 exe，无进程间协议，无需上述内容。）

### 技术选型

- PC 端：WebSocketSharp 或 Fleck
- VR 端：WebSocketSharp 或 Best HTTP

## ADR-003: 双模式文字输出（OSC + 剪贴板）

### 状态

✅ 已接受

### 背景

用户选好候选词后，需要将文字"输入"到 VRChat 中。需要决定文字输出的方式。

### 考虑的方案

| 方案 | 描述 | 适用场景 | 优点 | 缺点 |
|------|------|----------|------|------|
| **A. OSC `/chatbox/input`** | 通过 OSC 协议发送到 VRChat 聊天框 | VRChat 聊天框 | 不需要焦点；直接发送 | 只能用于聊天框 |
| **B. 剪贴板 + Ctrl+V** | 复制到剪贴板，模拟粘贴 | 任意输入框 | 通用 | 需要焦点 |
| **C. SendInput** | 模拟键盘逐字输入 | 任意输入框 | 不依赖剪贴板 | 慢；中文可能有问题 |
| **D. 进程注入** | 直接写入 VRChat 内存 | 任意场景 | 最直接 | 复杂；可能被反作弊检测 |

### 决策

选择 **双模式输出**：方案 A（OSC）作为默认，方案 B（剪贴板）作为备选

### 理由

#### 为什么选择双模式？

1. **OSC 模式的限制**：
   - VRChat 的 OSC API 只支持 `/chatbox/input`，只能发送到聊天框
   - 搜索框、Udon UI 输入框等场景 OSC 无法使用

2. **剪贴板模式的限制**：
   - 需要 VRChat 窗口有焦点
   - 如果用户在操作其他窗口，粘贴会失败

3. **互补关系**：
   - OSC 模式：聊天场景（最常用），体验最好
   - 剪贴板模式：其他输入框场景，通用性强

#### 场景覆盖

| 场景 | OSC 模式 | 剪贴板模式 |
|------|----------|------------|
| VRChat 聊天框 | ✅ 最佳 | ⚠️ 可用 |
| VRChat 搜索框 | ❌ 不支持 | ✅ 可用 |
| Udon UI 输入框 | ❌ 不支持 | ✅ 可用 |
| 其他 VR 应用 | ❌ 不支持 | ✅ 可用 |

### 后果

- 需要实现两套输出逻辑
- 需要提供用户切换模式的 UI
- 需要处理剪贴板模式下的焦点检测

## ADR-004: PC 端使用 .NET 而非其他语言

### 状态

❌ 已废弃（采用 ADR-009 单 exe 架构，无独立 PC 端程序）

### 背景

PC 端服务需要处理 WebSocket 通信、输入法交互、文字输出等功能。需要选择合适的开发语言和运行时。

### 考虑的方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. .NET 6/7 (C#)** | 使用 .NET 开发 | 跨平台；与 Unity 同语言；Windows API 互操作好 | 需要安装运行时 |
| **B. Python** | 使用 Python 开发 | 开发快；库丰富 | 性能一般；打包复杂 |
| **C. C++** | 使用 C++ 开发 | 性能最高；Windows API 直接调用 | 开发复杂；内存管理困难 |
| **D. Node.js** | 使用 Node.js 开发 | WebSocket 支持好；开发快 | Windows API 调用不便 |
| **E. Go** | 使用 Go 开发 | 性能好；部署简单 | Windows API 调用不便 |

### 决策

选择 **方案 A：.NET 6/7 (C#)**

### 理由

1. **与 VR 端同语言**：VR 端使用 Unity (C#)，PC 端也用 C#，代码可以共享（如消息类型定义）
2. **Windows API 互操作**：.NET 与 Windows API 互操作非常方便（P/Invoke）
3. **跨平台潜力**：虽然目前只支持 Windows，但未来可以扩展到其他平台
4. **成熟的库生态**：WebSocket、JSON、OSC 等都有成熟的库
5. **性能足够**：输入法处理对性能要求不高，.NET 完全可以满足

### 后果

- 用户需要安装 .NET 运行时（可以打包为单文件自包含应用）
- 开发需要 Visual Studio 或 VS Code + C# 扩展

## ADR-005: VR 端使用 Unity 2022.3 LTS

### 状态

✅ 已接受

### 背景

需要开发一个 Unity 应用来实现 SteamVR Overlay（并承载输入法与输出，见 ADR-009）。需要选择合适的 Unity 版本。

### 考虑的方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. Unity 2022.3 LTS** | 使用 Unity 2022.3 长期支持版本 | 稳定；长期支持；兼容性好 | 不是最新版本 |
| **B. Unity 2023.x** | 使用 Unity 2023 最新版本 | 最新特性 | 可能不稳定；兼容性待验证 |
| **C. Unreal Engine** | 使用虚幻引擎 | 渲染能力强 | 学习曲线陡；C++ 开发 |
| **D. Godot** | 使用 Godot 引擎 | 开源免费 | SteamVR 支持不完善 |

### 决策

选择 **方案 A：Unity 2022.3 LTS**

### 理由

1. **长期支持**：LTS 版本有 2 年的支持周期，稳定性有保障
2. **SteamVR 兼容性**：SteamVR Unity Plugin 对 LTS 版本兼容性最好
3. **社区资源**：LTS 版本使用人数多，遇到问题容易找到解决方案
4. **生产就绪**：LTS 版本经过充分测试，适合生产环境

### 后果

- 可能无法使用 Unity 2023 的新特性
- 需要确保使用的第三方库兼容 2022.3

## ADR-006: WebSocket 端口选择 8765

### 状态

❌ 已废弃（单 exe 架构下无 WebSocket，见 ADR-009）

### 背景

PC 端 WebSocket 服务器需要监听一个端口。需要选择合适的端口号。

### 考虑的方案

| 端口 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **80** | HTTP 默认端口 | 知名端口 | 需要管理员权限；可能与 Web 服务器冲突 |
| **8080** | HTTP 备用端口 | 常用 | 可能与其他开发服务器冲突 |
| **9000/9001** | VRChat OSC 端口 | 与 VRChat 相关 | 可能与 OSC 冲突 |
| **8765** | 非常用端口 | 不太会冲突 | 无 |
| **随机端口** | 每次启动随机选择 | 无冲突 | 配置复杂；防火墙问题 |

### 决策

选择 **端口 8765**

### 理由

1. **非常见端口**：8765 不是任何常见服务的默认端口，不太会冲突
2. **易于记忆**：8765 是一个有规律的数字，易于记忆
3. **无需管理员权限**：高于 1024 的端口不需要管理员权限
4. **可配置**：在配置文件中可以修改，如果 8765 被占用

### 后果

- 如果用户电脑上 8765 被占用，需要修改配置
- 需要在文档中说明如何修改端口

### 配置示例

```json
{
  "websocket": {
    "host": "127.0.0.1",
    "port": 8765
  }
}
```

## ADR-007: 使用 Windows TSF 而非第三方拼音库

### 状态

✅ 已接受

### 背景

需要将拼音转换为候选词。需要决定使用系统输入法 API 还是第三方拼音库。

### 考虑的方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. Windows TSF** | 使用 Windows Text Services Framework | 使用系统输入法；词库丰富；用户词库同步 | API 复杂 |
| **B. ImmGetCompositionString** | 使用传统 IMM API | 简单 | 已过时；Win10+ 支持有限 |
| **C. 第三方拼音库** | 如 pinyin4net | 实现简单 | 词库有限；需要自己维护 |
| **D. 在线 API** | 调用百度/搜狗 API | 词库大 | 需要网络；隐私问题 |

### 决策

选择 **方案 A：Windows TSF**

### 理由

1. **使用系统输入法**：TSF 可以直接使用用户已安装的中文输入法（微软拼音、搜狗等）
2. **词库丰富**：系统输入法词库大，且支持用户自定义词库
3. **用户习惯**：用户熟悉的输入习惯（如模糊音、双拼等）可以保留
4. **长期支持**：TSF 是 Windows 官方推荐的 API，长期支持

### 备选方案

如果 TSF 实现过于复杂，可以考虑：
- 方案 C（第三方拼音库）作为备选
- 使用 pinyin4net 或类似的库

### 后果

- TSF API 较复杂，开发难度较高
- 只支持 Windows，无法跨平台
- 需要处理不同输入法的兼容性问题

## ADR-008: OSC 库选择 OscCore

### 状态

✅ 已接受

### 背景

需要在 Unity 进程内通过 OSC 协议发送消息到 VRChat。需要选择合适的 OSC 库。

### 考虑的方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. OscCore** | VRChat 团队使用的 OSC 库 | VRChat 官方使用；性能好；兼容性好 | 文档较少 |
| **B. Rug.Osc** | 常用的 .NET OSC 库 | 文档完善；使用广泛 | 不是 VRChat 使用的 |
| **C. 自己实现** | 手写 OSC 协议 | 完全控制 | 工作量大；容易出错 |

### 决策

选择 **方案 A：OscCore**

### 理由

1. **VRChat 官方使用**：OscCore 是 VRChat 内部使用的 OSC 库，兼容性最好
2. **性能优秀**：OscCore 是高性能实现，适合实时应用
3. **维护活跃**：由 VRChat 团队维护，与 VRChat 的 OSC API 保持同步

### 后果

- 文档较少，可能需要查看源码
- 需要确保使用正确的分支（all-in-one）

### 使用示例

```csharp
using OscCore;

// 创建 OSC 客户端
var client = new OscClient("127.0.0.1", 9000);

// 发送聊天消息
// /chatbox/input <string> <bool> <bool>
// 参数1: 要发送的文字
// 参数2: 是否直接发送（true）还是打开输入框（false）
// 参数3: 是否播放通知音效
client.Send("/chatbox/input", "你好", true, false);
```

## ADR-009: 单 exe 架构（TSF 在 Unity 进程内）

### 状态

✅ 已接受

### 背景

早期方案为双进程：Unity Overlay + 独立 PC 端服务，通过 WebSocket 通信。用户反馈运行两个 exe 不可接受，且 TSF 可在 Unity 进程内通过 P/Invoke 或 C++ 插件调用，无需独立进程。

### 考虑的方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. 单 Unity exe** | Overlay + TSF + OSC 均在 Unity 进程内 | 只运行一个程序；部署简单 | 需在 Unity 内封装 TSF 调用 |
| **B. 双 exe（原方案）** | Overlay + 独立 PC 服务，WebSocket 通信 | 职责分离 | 用户需启动两个程序，不可接受 |
| **C. 单 .NET exe 自绘 Overlay** | 用 OpenVR 自绘 Overlay，无 Unity | 单 exe | 开发量极大，不选 |

### 决策

选择 **方案 A：单 Unity exe**

### 理由

1. **用户体验**：只需启动一个 VRCPinYin 应用，无需再开“后台服务”
2. **技术可行**：TSF 为 Windows API/COM，Unity 运行在同一 Windows 进程内，可通过 C# P/Invoke 或 C++ Native Plugin 调用
3. **架构简化**：无 WebSocket、无进程间协议，模块间直接调用即可

### 后果

- 仅一个 Unity 工程，模块为 5 个：Overlay 框架、虚拟键盘、候选词面板、输入法引擎、文字输出
- 输入法在 Unity 内通过 P/Invoke 或 C++ 插件调用 Windows TSF
